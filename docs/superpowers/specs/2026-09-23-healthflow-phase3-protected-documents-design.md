# HealthFlow Phase 3: Protected Documents and reusable record links

## Purpose and release boundary

OVE-139 lets a Broker keep one protected Document for one Client and reuse it across that Client's Enrollment, Issue, and Appeal without uploading duplicate files. Brokers can find, open, archive, and restore Documents; ending one Link does not archive the Document. Past Client and Document work remains traceable.

The first release is **synthetic-only**. The public Fly demo shows seeded Demo Documents but rejects every upload request at the server, even when a caller bypasses the UI. A separate private test environment, limited to trusted testers and synthetic fixtures, can upload invented files to its own bucket and database. Synthetic-only is an operating rule, not a claim that software can detect real health information inside arbitrary files. A real-data release needs its own application/database/bucket/secrets boundary and a separate review of provider agreements, security controls, malware handling, retention, backups, and recovery; this design does not claim that HealthFlow is ready for real data.

The demo's object-storage provider is a private Tigris bucket, selected in [ADR 0001](../../adr/0001-private-demo-document-storage.md). Demo Documents are replaceable fixtures: ordinary archive never destroys a file, but an explicit administrator reset can remove demo metadata and objects and reseed checked-in synthetic source files. Routine deploy seeding is idempotent and never revives an archived Document or duplicates its object. The demo bucket has no long-term backup requirement; recovery is reseeding. No automatic permanent purge runs against archived Documents. These rules do not establish retention or backup policy for future real Documents.

## Domain and data ownership

Each Document has a Broker owner and exactly one Client owner. Its metadata includes an opaque ID, encrypted display filename, verified file type, byte length, random object key, creation time, and optional archive time. User-supplied filenames never become bucket keys or filesystem paths. The bytes exist once in object storage, outside public static assets. The API never returns object keys or credentials.

Each Document Link associates one Document with exactly one Enrollment, Issue, or Appeal, enforced by typed foreign keys and an exactly-one-target constraint. The target must belong to the same Broker and Client; for an Appeal, the Client is established through its Issue. At most one active Link can connect a Document to a given target. A Link holds creation and end times so Unlink ends only that association and preserves its history. Re-linking creates a new Link; it does not erase the ended one. A Document always remains on its Client even with zero active Links. Document archive hides it from every active list without changing its Links. Restore re-exposes only Links that are still active; previously unlinked targets stay unlinked. The owning Broker can still find and open archived Documents in an Archive view. Reuse is by Link, not global deduplication of independently uploaded files.

Client deletion changes to archive, as decided in [ADR 0002](../../adr/0002-archive-clients-to-preserve-work.md). An archived Client is omitted from active Client lists and new-work selectors, but its profile and related history remain accessible and restorable. Existing Enrollment, Issue, Appeal, Document, Task, and Appointment records keep their IDs and states. Open Tasks and scheduled Appointments stay in Today/Scheduling with an archived-Client indicator; archiving does not silently cancel a deadline. Starting new work for an archived Client requires restoring it. The existing `DELETE /clients/{id}` API becomes a compatibility alias for archive, not hard deletion; the UI uses explicit Archive and Restore actions. There is no ordinary permanent-delete endpoint for Clients or Documents.

## Components and user flow

The document storage adapter owns private object `put`, `get`, and administrator-only `remove` operations. Tigris is the deployed S3-compatible adapter; tests use a fake adapter, and local development may use a private directory outside the served webroot. The document service owns file validation, Broker/Client/target checks, archive and Link transitions, and audit writes. API routes expose Client Documents, related-record Documents, archived Documents, upload where enabled, authenticated content opening, Link/Unlink, and archive/restore. The React workspace adds a Client Documents section and an Archive view; Enrollment, Issue, and Appeal surfaces show their active Document Links. The public demo offers no upload control.

Private-test upload requires an authenticated Broker and an active owned Client. `DOCUMENT_UPLOAD_ENABLED` defaults to false, and startup refuses `SEED_DEMO=1` together with enabled uploads; the public demo keeps `SEED_DEMO=1`. The server streams input under a configurable 20 MiB maximum, an allowlist of PDF, DOC, DOCX, JPG/JPEG, and PNG, and content-based checks rather than trusting extension or browser-provided MIME type. PDF and image signatures/structure are checked; DOC must be a Word OLE container, and DOCX must have a bounded, valid Word ZIP structure. Malformed, mismatched, oversized, or empty files are rejected before creating visible metadata. File names are sanitized for display, and object keys are generated independently. This validation limits accidental and disguised file types; it is **not** a malware scan. The first release does not enable uploads in the public demo or real-data environments.

After validation, the service writes one object and commits its Document metadata. The object store and database cannot share a transaction: on database failure after upload, the service attempts object cleanup and emits a metadata-only operational error if cleanup also fails, enabling narrow orphan reconciliation. No half-created Document is exposed to a Broker. A storage failure returns a retryable error without committed Document metadata. Reseeding and reset operate only on explicitly identified demo objects, never on a whole bucket or a future real-data namespace.

For opening, the server loads the Document under the current Broker, checks its Client and requested context, records a durable file-open audit event, and then streams bytes from the private store. Archived content remains openable to its owning Broker, but only the Archive/history UI lists it. PDF and images may be served inline with a verified content type, safe disposition, `Cache-Control: private, no-store`, and `X-Content-Type-Options: nosniff`; DOC/DOCX are attachments with the same cache and sniffing protections. No public Tigris URL, presigned URL, or storage credential is sent to the browser. Missing objects or unavailable storage return a service error rather than an empty file or public fallback.

## Authorization, audit, and failure behavior

Document and Link models join the tenant-scope registry and PHI-audit coverage. Every Link, Unlink, archive, restore, and Client archive/restore checks current Broker ownership. Link targets are loaded and checked against the Document's Client before writing; a matching record ID from another Broker or Client is rejected. Cross-Broker reads and mutations return the same not-found response as a nonexistent ID, including archived objects. The storage adapter never accepts an arbitrary client-supplied key.

The existing database audit covers Document/Link metadata access. Explicit durable events cover file-open attempts and outcomes, upload, Link/Unlink, Document archive/restore, and Client archive/restore. Events identify actor, Document/Client IDs, action, outcome, and time; they never record file bytes, storage credentials, or sensitive filenames. If the required audit write fails, protected bytes are not served. A stream interrupted after an open-start event may produce a separate failure event; an open-start event is not represented as proof that the full download completed. This distinction is maintained in tests and operational review.

Invalid type/structure returns a validation error; oversize returns a size error; disabled upload returns an explicit unavailable response; unauthorized or mismatched associations return not found; storage outage returns retryable service failure. Each path preserves the invariant that the UI shows only committed Documents and that ordinary operations do not permanently delete their bytes.

## Verification and deployment gate

Backend tests cover every allowed format and rejected spoofed/malformed format, 20 MiB boundary, disabled public-demo upload by direct API call, random storage keys, metadata encryption, one object across multiple Links, same-Client and cross-Broker checks, archived viewing, Link history, restore behavior, Client archival with active Tasks/Appointments, audit success/failure, missing objects, and upload cleanup. Existing test reset must clear Document Links and Documents in dependency order before deleting Clients; no test cleanup touches non-test objects.

Frontend tests cover Client and related-record Document views, archive/restore, Unlink, archived-Client indicators, and public-demo upload absence. Local backend tests and frontend build must pass. Before a public-demo deployment, provision and verify the private Tigris bucket, configure secrets outside the repository, prove synthetic seeding and targeted administrator reset, verify upload remains disabled at the API, and run direct-route/browser checks for Document and Archive views. A healthy `/health` alone is not document-route proof. These checks establish only the synthetic demo release, not real-data or regulatory readiness.
