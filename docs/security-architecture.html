HealthFlow · Security Architecture

The safest check is the one a developer cannot forget.

HealthFlow handles patient health data — medications, conditions, doctors. The dangerous failure isn't a clever attack; it's a missing WHERE broker_id clause one tired afternoon. So the protections that matter aren't left to memory. They are enforced once, centrally — in the database session, the type system, and listeners installed at startup — and they hold even when someone forgets.

The problem

Memory is the leak.

A multi-tenant health app asks every route to do the same chores by hand. Each one is a place to slip — and a single slip exposes one patient's record to the wrong broker.

The old way — every route remembers

  • ✕ Add WHERE broker_id = me to every query that touches patient data.
  • ✕ Strip names and conditions by hand before every call to the AI model.
  • ✕ Hope no one logs a raw patient record while debugging.
  • ✕ Remember to write an audit row for who-saw-what.

The guarantee lives in human discipline. Discipline does not scale.

The HealthFlow way — the system remembers

  • ✓ The filter is a property of the database session, not of each route.
  • ✓ PHI is redacted once by a typed object before any text can reach the model.
  • ✓ Sensitive columns are ciphertext on disk — the app never handles raw bytes.
  • ✓ Every PHI read and write logs itself, automatically.

Forgetting becomes structurally impossible, not merely discouraged.

The one idea to keep

Put the guard at the chokepoint.

Dozens of routes write queries, but every query — no matter who wrote it — flows through one object: the SQLAlchemy session. Attach the rule there once and every query inherits it. You stop guarding a hundred doors and start guarding the one hallway they all use.

One listener on the session filters every read. The route author doesn't ask for it and can't opt out.

Layer 1 · Tenant isolation

The query you wrote is not the query that runs.

A do_orm_execute event listener in database/tenant_filter.py inspects every statement. If it targets a tenant-scoped table, it appends WHERE broker_id = current_broker before the database ever sees it. The current broker comes from a request-scoped ContextVar that the auth dependency sets on every authenticated request.

  • ● Scoped models: Client, ActionHistory, Feedback.
  • ● Covers entity reads and column-selects like select(Client.id, Client.full_name).
  • ● A separate guard rejects raw SQL that tries to slip past the ORM.
— what the route author writes —
select(Client).where(Client.id == cid)
▼  session listener rewrites it  ▼
— what actually hits the database —
select(Client).where(
  Client.id == cid,
  Client.broker_id == current_broker,
)

A route that forgets the broker clause still cannot read another broker's patients — the result is simply None, and the route returns 404.

Layer 2 · The LLM boundary

Redact once, at the door to the model.

Five agents send data to Claude. None of them hand it a raw patient record. Each builds a frozen PromptInput dataclass that redacts free-text in its constructor — and a static AST test guarantees there is no code path from a raw string to a prompt body that skips it.

Drug/procedure names and doctor NPIs are not patient identifiers under this threat model, so they pass through deliberately. The audit event records only counts and types of what was redacted — never the text.

— on disk, a PHI column looks like —
v1:8Qf2…nonce…:b6Tz…ciphertext+tag…
— the app only ever sees plaintext —
client.full_name # "Eleanor Rigby"
# EncryptedString TypeDecorator
# encrypts on write, decrypts on read

Layer 3 · Encryption at rest

Ciphertext on disk, plaintext in code.

Eight PHI columns are stored as AES-256-GCM ciphertext. SQLAlchemy TypeDecorators do the work at the boundary, so application code never touches raw bytes. The wire format vN:nonce:ciphertext carries a key version, which makes key rotation additive rather than a migration.

  • ● A fresh random nonce per write — so the same name encrypts differently every time.
  • ● That randomness is the point: you can't equality-search an encrypted column, by design.
  • ● The key is read fail-loud at import — a missing or placeholder key crashes startup, loudly.

Layer 4 · The audit trail

Every patient record explains who touched it.

Every query against a PHI table writes an append-only row to phi_access_log — automatically, via two more session listeners. You never call an audit function; it fires on its own.

who

which broker

what

table + operation

whom

patient row IDs

why

request endpoint

when

timestamp

install order

The order is load-bearing: the audit listener is installed after the tenant filter, so it observes the query already scoped to the broker. The patient IDs it records are exactly the ones the broker was actually allowed to see — nothing more.

The whole picture

A request runs a gauntlet.

Two databases, deliberately unjoined: patient data in healthflow.db, public plan/ZIP reference data in healthflow_data.db. Keeping them separate is the data-classification boundary.

Proof it holds — a true story from this codebase

A whole pull request became unnecessary.

A branch proposed careful fixes: hand-add Client.broker_id == broker.id to the history routes so one broker couldn't read another's patient names, and validate ownership before writing a history row.

By the time it was reviewed, it was already redundant. The session filter had shipped — and it covers the exact column-select the branch was worried about (select(Client.id, Client.full_name)), and 404s a write that references another broker's client.

That is the architecture paying off: the protection was so thoroughly built into the foundation that a targeted, hand-written fix had nothing left to do.

If you add a new PHI table

Register it in three places.

The whole model rests on a table opting into the foundation. Miss a registry and the table silently bypasses a protection — so this is the one checklist worth memorizing.

  1. 1

    Tenant scope

    Add it to TENANT_SCOPED_MODELS in tenant_filter.py so its reads are auto-filtered by broker.

  2. 2

    Audit it

    Add it to _AUDITED_MODELS in phi_audit.py so every access lands in the append-only log.

  3. 3

    Encrypt the sensitive columns

    Wrap PHI columns in EncryptedString / EncryptedJSON and list them in the re-encryption sweep. Decide explicitly: encrypted, or a queryable quasi-identifier.

The takeaway: good security here is something you opt out of, not something you remember to opt into.
